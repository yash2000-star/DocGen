# Auth Routes

This file (`src/routes/auth.js`) defines the API endpoints responsible for user authentication. It handles user registration (signup), login, and logout functionalities, interacting with the `User` model and utility functions for validation and security. This module is registered with the main Express application (`src/app.js`) to expose the authentication routes.

## Overview

The `auth.js` module serves as the central router for user authentication within the application. It provides secure endpoints for users to create new accounts, log in to existing ones, and manage their session by logging out. This module is critical for user access control and integrates with `src/models/user.js` for database operations, `src/utils/validation.js` for input integrity checks, and `bcrypt` for password hashing and verification.

## Authentication Endpoints

This section details the available API endpoints for user authentication provided by the `auth.js` router.

### POST /signup

Registers a new user account. Upon successful registration, the provided password is hashed, a new user document is created in the database, a JSON Web Token (<Tooltip tip="JSON Web Token — a signed authentication credential">JWT</Tooltip>) is generated and set as an HTTP-only cookie, and the new user's data is returned.

<Warning>
  This endpoint handles sensitive user data, including passwords. Passwords are
  hashed using `bcrypt` before storage. The generated JWT token is stored in an
  HTTP-only cookie to mitigate Cross-Site Scripting (XSS) attacks. Ensure all
  inputs are validated to prevent injection attacks.
</Warning>

</ParamField>

</ParamField>

  A list of skills associated with the user.
</ParamField>
<ParamField name="photoUrl" type="string" optional>

### POST /login

Authenticates an existing user with their email and password. On successful authentication, the user's password is validated, a new JWT token is generated, set as an HTTP-only cookie, and the authenticated user's data is returned.

<Warning>
  This endpoint processes user credentials (email and password). The provided password is
  compared against its stored hash. A JWT token is issued upon successful
  login and stored in an HTTP-only cookie. Implement rate-limiting and other
  security measures to protect this endpoint from brute-force attacks.
</Warning>

<ParamField name="emailId" type="string" required>

</ParamField>
<ParamField name="password" type="string" required>

### POST /logout

Logs out the current user by clearing the JWT token cookie. This action effectively invalidates the user's session, requiring them to log in again for future authenticated requests.

<Danger>
  This action immediately clears the authentication token from the client's browser by
  setting its expiration to the past. While not destructive to user data, it
  will end the user's active session, and they will need to re-authenticate
  to access protected resources.
</Danger>

#### Parameters

This endpoint does not require any request body parameters. The logout operation relies on the browser sending the existing cookie, which the server then invalidates.

#### Response (200 OK)

<ResponseField name="message" type="string">
  A success message indicating that the logout was successful.
</ResponseField>

## Common Errors / Troubleshooting

<AccordionGroup>
  <Accordion title="400 Bad Request: Error saving the User">
    This error typically occurs during the `/signup` process if the provided user
    data fails validation. Common causes include missing required fields (e.g., `firstName`, `emailId`, `password`),
    an invalid email format, or an attempt to register with an `emailId` that
    is already in use. Review the request payload against the `/signup` parameters
    and ensure that `src/utils/validation.js` is correctly configured and applied.
  </Accordion>
  <Accordion title="400 Bad Request: Invaild credentials">
    This error is returned by the `/login` endpoint if the provided `emailId`
    does not correspond to an existing user in the database, or if the `password`
    does not match the stored hashed password for that user. Verify both `emailId`
    and `password` are correct. This can also indicate a <Tooltip tip="An attack that tries many passwords until the correct one is found">brute-force</Tooltip> attempt.
  </Accordion>
  <Accordion title="JWT Token not set in cookie">
    If the JWT token is not being correctly set as an HTTP-only cookie after
    a successful signup or login, investigate the server logs for any errors
    related to `res.cookie`. Additionally, ensure that your client-side environment
    (e.g., browser or API client) supports receiving and storing HTTP-only cookies
    from the server. Check `res.cookie` options like `expires`, `domain`, and `secure`
    to ensure they are appropriate for your deployment environment (e.g., `secure: true` for HTTPS).
  </Accordion>
  <Accordion title="Logout request does not invalidate session">
    If calling `POST /logout` does not invalidate the user's session (i.e., the
    token cookie persists), ensure that the `res.cookie` command used for
    logout correctly sets the token to `null` or an empty string with an `expires`
    date in the past. Verify that the client is indeed sending the cookie in
    the logout request header so the server can target and invalidate it.
  </Accordion>
</AccordionGroup>
